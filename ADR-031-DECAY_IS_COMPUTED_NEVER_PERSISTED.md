## Context

The deep audit of the learner model (2026-10-01) found that forgetting decay compounded. One root cause, two surfaces:

1. **The nightly batch persisted its own output.** `SkillState.applyDecay` (core `SkillState.java:92-95` @ `cd9e5747`) wrote the decayed value into `mastery` while leaving `last_practiced_at` untouched, and `NightlyDecayJob.runDecayPass` (`NightlyDecayJob.java:145-152`, persisted at `:172`) recomputed `decayed(state.mastery(), lastPracticedAt, now)` — the **full elapsed exponent** — against the already-decayed stored value. Decay became superlinear: each night multiplied by `e^(−Δt/τ)` again.
2. **Every learner-facing read surface re-decays the stored value on read** — `LearnerStateController.java:109`, `LearnerKnowledgeGraphService.java:116`, `ClassKnowledgeGraphService.java:318/340/508`, `NextBestActionService.java:162`, `SmartLessonService.java:897` — i.e. they already implement the contract that the stored value is the post-practice posterior P₀, exactly as `EbbinghausDecayService.decayed()` documents (`@param mastery stored mastery P₀ at lastPracticed`). The write-back made stored = decayed, so every read decayed an already-decayed value *again*.

A second accelerant: τ is selected by the band of the value passed in. As the stored value fell below 0.8 the band flipped 365d→90d→30d, accelerating further decay — a positive feedback loop. The audit's simulation (`scripts/decay_compound_sim.py`, faithful code-path emulation) quantified the distortion at Paper-B defaults: m₀=0.8 crosses the 0.6 review threshold on **day 8** (vs **day 26** on the no-write-back curve) and hits the 0.1 floor by **day 20** (no-write-back value 0.641); m₀=0.95 hits the floor by day 20 (no-write-back 0.899). The two-night micro-check attributes the nightly extra factor 0.9592 to write-back re-application (0.9918) × band flip (0.9671).

This was live: the job is enabled in production (T-C37 verified the Render chain), so every skill idle > 48h was over-decaying, review scheduling over-triggered, and DECAY_APPLIED telemetry (prior/effective) was distorted. The design comments show partial awareness — the stable-paging comment guarded against within-pass revisit compounding, and the `:148-149` comment ("re-running the decay formula on the stored value would double-count") protected the *review decision* — but the cross-night write-back compounding itself was missed, and the session-114 "a late run is exact" claim was reasoned on the incorrect no-compounding premise.

## Accepted

- **Stored is the anchor.** `skill_states.mastery` holds the BKT posterior at `last_practiced_at` — P₀. Forgetting decay is **computed at every read/pass** from (P₀, last_practiced_at, now) and **never persisted**. The nightly pass is read-only over `skill_states`; its only writes are the V38 ledger row and `review_schedules` inserts. `SkillState.applyDecay` is deleted.
- **Band frozen at practice.** τ is evaluated on the value the caller passes; callers pass P₀, so the decay rate is a property of the encoding (the post-practice estimate), not of the current decayed readout — matching the Paper B §3.3 retention-curve reading and eliminating the band-flip feedback loop by construction.
- **Correctness by the exponential semigroup.** With a stable anchor, N passes compose exactly: e^(−(t₁+t₂)/τ) = e^(−t₁/τ)·e^(−t₂/τ). Late/catch-up runs (V38 run-if-missed) are now genuinely exact, making the session-114 claim true for the first time. A same-instant rerun is idempotent.
- **Read surfaces unchanged.** The five re-decaying surfaces were already correct under this contract; the write path is aligned to them, not vice versa.
- **Raw readers re-scoped (resolves S3-1 by declaration).** Consumers of `state.mastery()` without re-decay (`ClassAnalyticsService`, `ClaService`, `LearnerContextAssembler`, `StruggleInferenceService`, `SmartLessonService` "mastery (raw)") now receive *ability at last practice* — the ability estimate — while decayed surfaces show *memory readiness*. Teacher analytics banding raw mastery is therefore intended semantics; switching teacher surfaces to effective mastery is a product decision, explicitly out of scope here.
- **Contention narrowed (C-4).** The batch no longer rewrites `skill_states` rows, so a submission can no longer conflict with the decay pass; the optimistic-lock version guards submission-vs-submission races only. Nightly write amplification (500-row pages rewritten) disappears.
- **Regression pinned.** `NightlyDecayJobTest.secondConsecutivePassDoesNotCompound` runs the checker twice against the same row and fails on pre-fix code (pass 2 reads ≈0.3206, emits ≈0.2056, writes through) and passes post-fix. `decayIsComputedFromTheAnchorNotPersisted` replaces the former `decayAppliesAndSchedulesReview`, which regrettably asserted the buggy write-through (`state.mastery()` ≈ 0.321 after the run).

## Rejected

- **(b) Incremental decay anchor** — persist decay plus a `last_decay_applied_at` column, applying only Δt since the last pass: not idempotent (a double tick or ledger race double-decays the interval), the band-on-current positive feedback survives damped, and mid-interval practice forces `max(lastDecayAppliedAt, lastPracticedAt)` footwork.
- **(c) Immutable `mastery_p0` column, job recomputes-and-writes effective nightly** — strictly dominated by this ADR: keeps the nightly write amplification and submission-vs-decay optimistic-lock conflicts, needs a backfill migration, keeps two mastery columns in sync in every writer — for zero additional correctness, since the read surfaces already recompute at read.
- **Persisting decay on read (write-behind cache)** — reintroduces the same split with extra moving parts.
- **Keeping write-back and removing re-decay from the five read surfaces** — would freeze every night's effective value as tomorrow's anchor: mastery would only move on fresh practice, DECAY_APPLIED telemetry would degenerate, and every missed-night catch-up would still lean on the full-elapsed assumption the V38 redesign was built on.

## Consequences / migration notes

- **No schema migration.** The column's meaning is redefined in code; the javadoc plus this ADR are the contract.
- **Existing rows carry write-back-era decayed values** (P₀ unrecoverable); reads will compute from those low anchors until the learner next practices. The error direction is conservative (mastery under-estimated → review over-scheduled). A one-time inverse backfill (P₀ = m·e^(+Δt/τ(P₀)) fixed point) was considered and deferred: reconstruction over-shoots under compounding corruption (stored values are not on the ideal curve), and pilot scale makes next-practice self-healing acceptable. Optional ops follow-up, not part of this change.
- **Telemetry discontinuity.** `DecayAppliedEvent.priorMastery` is genuinely P₀ from deploy onward; the research module should segment Cycle-1 mastery analytics at the deploy date. The ledger's `decayed` counter keeps its population (states whose computed effective dropped below the anchor — the same states that were event-published before).
- **Master Spec §11 wording** "forgetting decay applied nightly" is hereafter interpreted as *computed and reviewed nightly, persisted never*; the spec text update goes through the next spec sync. Under the frozen band the ideal curve for m₀=0.8 crosses the 0.6 review threshold at t ≈ 105 days (365·ln(0.8/0.6)) — slower than the audit's "ideal" day-26 figure, which still carried band-on-current semantics.
