## 6. Phase B — the operator validation lane (the ONLY path from SUGGESTED to HUMAN_VALIDATED)

**Instrument:** `graph/reports/C19_CONCEPT_SP_SUBSTRATE_REVIEW_SHEET.md` (C13 naming family), emitted by `c19_substrate_verify.py`: header records the seed, row count, class rollup, the anti-forgery reminder (*"the tool cannot emit HUMAN_VALIDATED rows; only your verdicts here can"*), and the per-class gate rule.

**Sampling (deterministic, sha256-seeded, no RNG — gold_spotcheck precedent; v1.1 §12-D drops the impossible "every concept" floor of v1.0):**
- 100% of non-CORE rows (6 ENRICHMENT + 3 SUPPORTING = 9);
- 20% stratified sample of CORE rows, stratified by section (S1/S3), ranked by `sha256(seed + identity)` within each stratum;
- 100% of rows that failed or warned on any mechanical check (M3/M4);
- every multi-attached SP (23 of them) contributes ≥1 of its rows — dual-attachment context is the actual identity-risk case (FP-B4-3);
- expected sample ≈ 30–39 rows.

**Per-row method (recorded on the sheet, C13 two-layer standard):** *mechanical* — the row's M1–M5 ledger result is re-displayed; *semantic* — the reviewer judges whether the CONCEPT (title, aliases, definition scope) genuinely subsumes the SP's demand, using the quote(s) as evidence against the SP's official wording and the note context — the note-level note→SP link is already operator-validated upstream (T-C10); the new judgment is concept-level topical fidelity. Verdicts: **CONFIRM / REJECT / HOLD**; every verdict line carries an optional reviewer note; HOLD must state what evidence would unblock it.

**Gate arithmetic (per class = role × section, C13 rule):** confirmed-precision **≥ 90%** per class; **all** sampled rows decided (no silent skips). Any class below 90% → rework that class (substrate fix or evidence improvement) and re-gate **that class**; the sheet version bumps and the failed gate stays on record. With 117 rows the expected sample is ~32–35 rows.

**Reviewer identity & authority:** the operator (or operator-delegate under the operator's explicit instruction, C13 precedent — the human retains final sign-off and nothing flips until §7 apply).

## 7. Phase C — promotion apply: the attachment-promotion pathway (v1.1 §12-B/C — rebuilt from the real mechanics)

Self-review against the actual code changed this section materially. Three facts drive the design:
1. `c11_promote.py` **refuses PART_OF by design** (*"PART_OF edges are DERIVED from node attachments… node promotion is a separate identity decision, expansion round"*) — T-C19 IS that expansion round, so the pathway must be built, not worked around.
2. The generator **derives PART_OF edges from node attachments and copies the NODE's validation_status onto them** — which is why all 117 are SUGGESTED. A direct store write (C13-style) would be reverted by the next generator re-run and flagged by graph_check — the architecture explicitly forbids it (*"hand-edits of the graph are reverted by re-runs and rejected by graph_check (c11.10)").*
3. `graph_check.py` c11.10 **hard-fails any HUMAN_VALIDATED PART_OF edge** (*"node promotion pathway not built"*) — the checker must learn the new pathway in the same change, or the apply can never go green.

**The pathway (three additive, property-preserving pieces):**

- **`scripts/c19_promotions.yaml`** — the operator-side attachment-promotion record (the c10/c11/c12 promotions-file family). Entries: `{attachment: {concept, spec_point}, validated_by, validated_date, review_reference}` — exact PART_OF identity, one entry per confirmed row. Written ONLY by `c19_promote.py`; hand-editing forbidden; atomic replace.
- **`scripts/c19_promote.py`** (new, c11_promote family discipline): takes the filled sheet's CONFIRM verdicts as exact identities; pre-verifies each (attachment exists in the store as a derived row; evidence quotes byte-verify via the shared T-C10 `norm()`; attribution gate — no AI-name in `validated_by`; ISO date; review-ref file exists); records idempotently; then triggers the gated generator re-run. Exit 0 = recorded + generator green.
- **`c11_concept_pilot.py` extension (additive, minimal — the G19 gate):** loads `scripts/c19_promotions.yaml` if present (absent file = zero entries); validates every entry (shape, PART_OF relation, attribution, ISO date, review-ref resolvable, attachment resolves to a CONCEPT node's declared spec_points attachment, no duplicates); stamps the derived PART_OF edge `validation_status: HUMAN_VALIDATED` + `validated_by`/`validated_date` (the §18 precedent fields; evidence/provenance/confidence/ambiguity_note preserved verbatim; **tier stays AI_SUGGESTED — origin is immutable**); adds `attachment_promotion_record` to the edges meta ONLY when entries exist. **Zero c19 entries ⇒ byte-identical emission (the G13 property, preserved and proven).**
- **`graph_check.py` c11.10 amendment (additive):** PART_OF HUMAN_VALIDATED edges are legal **only** with an exact match in `c19_promotions.yaml` (same exact-match + attribution discipline as c11.13 applies to semantic edges via `c11_promotions.yaml`); the c19 record itself gets schema/attribution validation; all other PART_OF constraints (source CONCEPT, target in-scope SP, role vocabulary, attachment set == declared) unchanged.

**Verdict semantics (v1.1 §12-C field fix — edges carry no `damage_flags`):** CONFIRM → recorded → HUMAN_VALIDATED at generation. HOLD → stays SUGGESTED; the reviewer's unblock condition is recorded on the sheet and in the substrate verification ledger (the row's `ambiguity_note` is store-owned and only the generator writes it — the lane records intent, the generator writes state). REJECT → stays SUGGESTED; recorded in the sheet + apply record as a mapping-question finding that returns to T-C11's decision-record process; never silently deleted.

**Reproduction + survival proofs (both mandatory at apply):** (i) Phase A re-run at the same pins reproduces the rows byte-identically; (ii) **byte-identity of the zero-c19 state**: the patched generator run with no `c19_promotions.yaml` produces store files byte-identical to the pre-patch emission (proves the extension is purely additive); (iii) with the record present, exactly the recorded rows flip; (iv) graph_check green on the promoted store; (v) idempotent re-run.
